\section{Introduction}

This document is a reference manual to \href{https://github.com/thousandbrainsproject/tbp.monty}{\texttt{TwoDSensorModule}} as implemented in \texttt{tbp.monty} version \texttt{0.33.0}. The document will cover results and explanation of how and why certain algorithms are implemented, and also point out limitations and areas for improvement. The manual will be detailed enough for someone who is interested in improving any part of the TwoDSensorModule to have a good understanding on why certain things were chosen and get a guide for where to go.

The implementation of TwoDSensorModule was roughly divided into two phases:

\begin{enumerate}
  \item Detecting dominant edge in a patch
  \item Implementing 2D Movement
\end{enumerate}

\subsection{\texttt{StructureTensor}}

\textbf{The Problem.}
A Sobel gradient at one pixel gives a local direction of intensity change,
but a sensor patch contains thousands of such gradients. Some gradients come
from the dominant texture edge, some come from noise, and some come from
secondary texture. We need a compact way to summarize whether the patch
contains one coherent orientation or many competing orientations.

A simple average of gradient angles is not sufficient. Angles wrap around,
opposite gradients can describe the same edge, and weak gradients from flat
regions should not count the same as strong gradients near an edge. The
representation must preserve orientation evidence without committing too
early to a single angle.

\textbf{The Solution.}
\texttt{StructureTensor} stores the second-order gradient statistics for a
local image region:
\[
  J =
  \begin{bmatrix}
    J_{xx} & J_{xy} \\
    J_{xy} & J_{yy}
  \end{bmatrix}
  =
  \begin{bmatrix}
    I_x^2 & I_x I_y \\
    I_x I_y & I_y^2
  \end{bmatrix}
\]
In \texttt{EdgeDetector}, this tensor is first computed per pixel and
Gaussian-smoothed, then the smoothed tensors are aggregated over the patch
with center-biased weights. After aggregation, \texttt{StructureTensor}
represents the dominant gradient statistics of the whole weighted patch.

The eigenvectors of $J$ identify the directions of smallest and largest
gradient variation. The largest eigenvalue, $\lambda_{\max}$, measures how
much gradient energy exists in the dominant gradient direction. The smallest
eigenvalue, $\lambda_{\min}$, measures how much gradient energy exists in the
orthogonal direction. A clean straight edge has one large eigenvalue and one
small eigenvalue. A corner, junction, or isotropic texture has two more
similar eigenvalues because gradient energy exists in multiple directions.

\textbf{Orientation, Strength, and Coherence.}
The dominant gradient direction is computed directly from the tensor entries:
\[
  \theta_g =
    \frac{1}{2}
    \arctan2(2J_{xy}, J_{xx} - J_{yy})
\]
The factor $\frac{1}{2}$ is load-bearing. The tensor describes orientation,
not a signed vector direction, so the relevant space is modulo $\pi$ rather
than modulo $2\pi$. The doubled-angle formula lets the tensor combine
opposite gradients that correspond to the same undirected edge.

The edge tangent is perpendicular to the gradient direction:
\[
  \theta_e = \theta_g + \frac{\pi}{2}
\]
The implementation wraps this value into the range used by the downstream
edge pose code. In practice the detected edge orientation is undirected:
angles that differ by $\pi$ describe the same edge line.

Edge strength is:
\[
  \sqrt{\lambda_{\max}}
\]
This returns the dominant gradient magnitude scale rather than the squared
energy scale stored in the tensor. Coherence is:
\[
  \frac{\lambda_{\max} - \lambda_{\min}}
       {\lambda_{\max} + \lambda_{\min}}
\]
with a zero fallback when the eigenvalue difference is below tolerance. This
score is close to 1 when the patch has one dominant orientation and close to
0 when the gradient evidence is isotropic or ambiguous.

\textbf{Subtle Details.}
The tensor components are squared before smoothing or aggregation. This is
what preserves local gradient energy. Smoothing $I_x$ and $I_y$ first would
allow nearby opposite gradients to cancel before the tensor is formed,
weakening the orientation estimate.

The tensor also separates ``how much edge evidence exists'' from ``how
coherent that evidence is.'' A high-contrast corner can have high strength
but low coherence, while a faint but clean line can have lower strength and
higher coherence. \texttt{EdgeDetector} therefore thresholds both values.

\subsection{\texttt{\_gradient\_to\_tangent\_angle}}

\textbf{The Problem.}
\texttt{StructureTensor.gradient\_theta} gives the dominant gradient
direction, but the feature passed to the 2D sensor is an edge tangent. The
gradient points normal to an edge: it points across the intensity change,
not along the line that the sensor should use as the local edge direction.

There is also an angle-convention issue. The current structure-tensor
detector represents undirected edge orientation. A line at angle $\theta$ and
the same line at angle $\theta + \pi$ describe the same edge. Future
directional edges, such as distinguishing light-to-dark from dark-to-light,
would require preserving gradient polarity somewhere else in the detector.
The current tensor has already squared and multiplied gradients, so opposite
gradient signs have been intentionally collapsed.

\textbf{The Solution.}
\texttt{\_gradient\_to\_tangent\_angle} rotates the gradient direction by
$\frac{\pi}{2}$:
\[
  \theta_e = \theta_g + \frac{\pi}{2}
\]
This converts a normal direction into the corresponding tangent direction.
The implementation then wraps the result with:
\[
  (\theta_e + 2\pi) \bmod 2\pi
\]
so the returned value is always non-negative and less than $2\pi$.

In current use, this helper is called from \texttt{StructureTensor.edge\_angle}.
That call site supplies \texttt{gradient\_theta}, which comes from the
half-angle structure-tensor formula and represents an undirected orientation.
Downstream tests therefore compare detected edge angles modulo $\pi$, because
$\theta$ and $\theta + \pi$ are equivalent for the present detector.

\textbf{Subtle Details.}
The helper itself wraps to $[0, 2\pi)$; it does not by itself enforce an
undirected $[0, \pi]$ range for arbitrary inputs. The effective undirected
range comes from the structure-tensor caller, not from the modulo operation in
this helper. This distinction matters if a future detector introduces
directional edge polarity. In that case, preserving $[0, 2\pi)$ can be useful,
but the detector would also need a source of signed gradient information that
the current tensor representation no longer contains.

\textbf{Gotchas.}
The lower endpoint of the practical edge-angle range is sensitive to IEEE 754
signed zero behavior. For a horizontal or vertical idealized tensor,
\texttt{arctan2(+0.0, negative)} returns $\pi$, while
\texttt{arctan2(-0.0, negative)} returns $-\pi$. Because the structure tensor
usually produces positive zero for \texttt{Jxy = Ix * Iy}, the wrapped tangent
angle lands at $\pi$ rather than $0$. The tests therefore treat edge
orientation as modulo $\pi$ instead of depending on one endpoint convention.

\subsection{\texttt{EdgeDetector}}

\textbf{The Problem.}
This feature was initially posed as an edge detection problem, but the
actual problem is more specific. The 2D sensor does not only need to know
whether an edge exists at a single center pixel. It needs to know whether
there is a dominant edge in the observed $64 \times 64$ patch and, if so,
what orientation that edge has. This is different from other local feature
extractors that read the feature value at the patch center. Texture edges
can pass near the center, occupy only part of the patch, or appear together
with other weaker edges. The detector therefore needs a notion of dominant
orientation that is global enough to be stable but still biased toward the
center of the patch.

The same image at different zoom levels can produce different dominant edge
orientations. A line that fills most of the patch at one scale can become a
small off-center detail at another scale. For this reason the patch size,
radial weighting, and detection thresholds are part of the algorithm rather
than incidental implementation details.

\textbf{The Solution.}
The main algorithm that performs dominant edge detection, orientation
estimation, edge strength computation, and coherence computation is
implemented by the \texttt{\_\_call\_\_} method of \texttt{EdgeDetector}.
The class replaces the
earlier standalone \texttt{compute\_edge\_features} function while
preserving the same conceptual algorithm. The callable class structure lets
\texttt{TwoDSensorModule} hold a configured detector instance and establishes
the pattern for future feature detectors.

Given a \texttt{SensorObservation}, the detector first extracts
\texttt{observation["rgba"][:, :, :3]} and interprets those channels as RGB.
This is upheld by the current \texttt{SensorObservation} path, where the
color patch is RGBA with red, green, and blue in that order. A caller that
constructs observations from images loaded with OpenCV must be careful:
\texttt{cv2.imread} returns BGR, so such images need to be converted to RGB
before being placed in the \texttt{rgba} field. Otherwise
\texttt{cv2.COLOR\_RGB2GRAY} uses the wrong luminance weights, which can
shift the gradients and the resulting edge orientation.

The detector then converts the RGB patch to grayscale and computes Sobel
gradients:
\[
  I_x = \texttt{Sobel}(I, 1, 0), \quad
  I_y = \texttt{Sobel}(I, 0, 1)
\]
From these gradients it builds a per-pixel structure tensor:
\[
  J =
  \begin{bmatrix}
    I_x^2 & I_x I_y \\
    I_x I_y & I_y^2
  \end{bmatrix}
\]
Each tensor component is Gaussian-smoothed before aggregation. This order is
intentional: smoothing $I_x^2$, $I_y^2$, and $I_x I_y$ estimates the local
second-moment structure, whereas smoothing $I_x$ and $I_y$ first and then
squaring would suppress opposing gradients before they contribute to the
orientation estimate.

The per-pixel tensors are then reduced to one representative tensor for the
patch using a center-biased weight map:
\[
  w(r, c) =
    \exp\left(-\frac{d(r, c)^2}{2\sigma_r^2}\right)
    \left(I_x(r, c)^2 + I_y(r, c)^2\right)
\]
with weights outside \texttt{radius} set to zero. The radial term makes
central gradients count more than peripheral gradients, while the gradient
magnitude term makes flat pixels contribute zero. This is what lets the
detector estimate a dominant patch-level edge without becoming a pure
whole-image average.

The aggregated tensor has two eigenvalues, $\lambda_{\min}$ and
$\lambda_{\max}$. Edge strength is defined as $\sqrt{\lambda_{\max}}$.
Coherence is defined as:
\[
  \frac{\lambda_{\max} - \lambda_{\min}}
       {\lambda_{\max} + \lambda_{\min}}
\]
with a zero fallback when the eigenvalue difference is below tolerance.
Coherence measures how strongly the patch evidence prefers one orientation:
it is high for a clean single edge and low for isotropic texture, corners, or
multiple competing edge directions. The final boolean
\texttt{has\_edge} is true only when edge strength exceeds
\texttt{strength\_threshold} and coherence exceeds
\texttt{coherence\_threshold}.

\textbf{Center Bias and \texttt{max\_center\_offset}.}
Radial weighting and \texttt{max\_center\_offset} solve different problems.
Radial weighting is continuous and always participates in the orientation
estimate: it downweights gradients far from the center but still allows a
strong off-center edge to influence the aggregate. By contrast,
\texttt{max\_center\_offset} is an optional hard rejection rule. Once an
orientation has been estimated, the detector projects the weighted gradient
evidence onto the detected edge normal and computes how far the weighted edge
centerline is from the patch center. If that distance is larger than
\texttt{max\_center\_offset}, the detector returns no edge.

The default value is \texttt{None}, so this hard center check is disabled.
The option is mainly useful for reducing extra edge clutter during
visualization. It does not replace radial weighting, because it operates
after the dominant orientation has already been estimated.

\textbf{Geometric Edge Check.}
\texttt{EdgeDetector} also checks whether the detected RGB edge corresponds
to a depth discontinuity. It computes Sobel gradients on the depth patch,
takes the depth gradient at the center pixel, and projects that gradient onto
the direction perpendicular to the RGB edge. If this perpendicular depth
gradient exceeds \texttt{depth\_edge\_threshold}, the edge is marked as a
geometric edge.

This matters because \texttt{TwoDSensorModule} is interested in texture
edges on a 2D surface, such as the edge of a logo on a mug, not object
boundaries or surface creases. \texttt{EdgeDetector} only reports
\texttt{is\_geometric\_edge}; the filtering decision happens in
\texttt{TwoDSensorModule.\_extract\_2d\_edge}. The default
\texttt{depth\_edge\_threshold} is \texttt{0.01}, which corresponds to about
one centimeter when depth is measured in meters.

\textbf{Parameter Choices and Limitations.}
Several defaults are pragmatic rather than analytically derived.
\texttt{kernel\_size=7} is a remnant from an earlier version that focused on
edges in a small center region. \texttt{radius=14.0} was chosen as a
reasonable center neighborhood for a $64 \times 64$ patch.
\texttt{sigma\_r=7.0} controls the radial Gaussian falloff, but its exact
value has not been justified independently. \texttt{coherence\_threshold=0.5}
is a middle-of-range requirement on a score bounded between 0 and 1.
\texttt{strength\_threshold=0.1} is intentionally low so weak but coherent
texture edges are still detected.

The detector returns one dominant orientation. It cannot represent two edges,
a corner, a junction, or repeated strokes in the same patch except by reducing
coherence or producing a compromise orientation. The geometric edge check is
also center-pixel based: it computes the full depth gradient image but samples
only the center depth gradient for classification. A noisy center depth value
can therefore mark a texture edge as geometric, or miss a depth discontinuity
that is nearby but not centered.

\textbf{Alternatives.}
We explored well-known edge detection methods such as Canny edge detection,
but Canny returns an edge-pixel mask rather than a compact dominant
orientation, strength, and coherence for a patch. A single-pixel Sobel angle
at the patch center would be closer to the old center-feature interpretation,
but it is brittle when the edge is slightly off center or noisy at the exact
center. A Gabor filter bank could test for edges at several orientations, but
it requires choosing a discrete orientation grid and running multiple
convolutions. The structure tensor gives a continuous orientation estimate in
one pass while still allowing center bias through the weight map.

\subsection{\texttt{EdgeFeatures}}

\textbf{The Problem.}
The edge detector produces several related quantities, and downstream code
needs to distinguish measurement from decision. A patch can contain enough
gradient evidence to estimate an orientation but still fail the detector's
thresholds because the edge is too weak or the gradient evidence is not
coherent enough. Conversely, a patch can fail before an orientation exists at
all, such as a uniform patch or an edge rejected by \texttt{max\_center\_offset}.

\textbf{The Solution.}
\texttt{EdgeFeatures} is the handoff object returned by
\texttt{EdgeDetector.\_\_call\_\_}. It stores:
\begin{itemize}
  \item \texttt{angle}: the estimated dominant edge orientation, or
        \texttt{None} when no reliable orientation was computed.
  \item \texttt{strength}: the dominant gradient magnitude scale.
  \item \texttt{coherence}: the orientation-quality score in $[0, 1]$.
  \item \texttt{is\_geometric\_edge}: whether the RGB edge corresponds to a
        depth discontinuity.
  \item \texttt{has\_edge}: the final thresholded detector decision.
\end{itemize}
\texttt{has\_edge} is the definitive decision flag. \texttt{angle} is an
estimated dominant orientation whenever the detector has enough gradient
evidence to compute one. A weak or low-coherence patch can therefore have a
non-\texttt{None} \texttt{angle} while \texttt{has\_edge} is false.

\textbf{Downstream Contract.}
\texttt{TwoDSensorModule.\_extract\_2d\_edge} uses \texttt{has\_edge} as the
first gate. If \texttt{has\_edge} is false, the original curvature-based pose
is left unchanged. If \texttt{has\_edge} is true but
\texttt{is\_geometric\_edge} is also true, the pose is also left unchanged,
because the 2D sensor is trying to represent texture edges on a surface rather
than object boundaries or surface creases. Only a detected non-geometric edge
is converted into 2D pose vectors.

\textbf{Gotchas.}
\texttt{angle is not None} is not equivalent to \texttt{has\_edge}. Treating a
non-\texttt{None} angle as a detected edge admits weak or incoherent patches
into the 2D pose pipeline. Treating \texttt{has\_edge} as the gate preserves
the detector's intended separation between diagnostic measurements and usable
edge features.

\textbf{Limitations.}
The dataclass does not encode why detection failed. A uniform patch and an
edge rejected by \texttt{max\_center\_offset} both return
\begin{itemize}
  \item \texttt{angle=None}
  \item \texttt{strength=0.0}
  \item \texttt{coherence=0.0}
  \item \texttt{is\_geometric\_edge=False}
  \item \texttt{has\_edge=False}
\end{itemize}
If future debugging or learning logic needs to distinguish these cases, the
result type will need an explicit rejection reason.

\subsection{\texttt{\_angle\_to\_pose\_2d}}

\textbf{The Problem.}
\texttt{EdgeDetector} is intentionally reusable. It can detect a dominant
edge orientation for \texttt{TwoDSensorModule}, \texttt{CameraSM}, or any
other sensor module that wants an image-space edge feature. The detected
angle by itself is still viewpoint-dependent: it is measured from the image
x-axis toward the image y-axis, i.e., downward in the image. A sensor module
must decide which reference frame should receive that orientation.

\texttt{\_angle\_to\_pose\_2d} is specifically the adapter for
\texttt{TwoDSensorModule}. It converts an image-space edge angle into pose
vectors expressed in the transported \texttt{TangentFrame}. This is different
from the earlier \texttt{edge\_angle\_to\_2d\_pose} formulation, which used a
scalar \texttt{world\_angle = ref - theta} and produced pose vectors in the
world $xy$ plane. That older path was useful for a flat world-XY
interpretation, but it was not the correct reference frame for the 2D sensor
moving over a curved surface.

\textbf{The Solution.}
The current function keeps the reference-frame conversion explicit. It first
maps the image axes into world coordinates:
\[
  x_{\mathrm{img}}^{w} = R[1, 0, 0]^T,
  \quad
  y_{\mathrm{img}}^{w} = R[0, -1, 0]^T
\]
where $R$ is the rotation component of \texttt{world\_camera}. The negative
sign in the image-y basis is load-bearing: image coordinates have positive
y downward, while the camera/world convention used here treats positive y in
the opposite direction.

The image-space edge angle is then converted into a world-space direction:
\[
  e^w =
    \cos(\theta) x_{\mathrm{img}}^{w}
    + \sin(\theta) y_{\mathrm{img}}^{w}
\]
This vector is projected onto the local surface tangent plane and normalized.
Finally, it is expressed in the transported tangent basis:
\[
  e^{2d} =
  \begin{bmatrix}
    e^w \cdot u \\
    e^w \cdot v \\
    0
  \end{bmatrix}
\]
where $u$ and $v$ are \texttt{tangent\_frame.basis\_u} and
\texttt{tangent\_frame.basis\_v}. The returned pose vectors are:
\[
  \begin{bmatrix}
    0 & 0 & 1 \\
    e_x^{2d} & e_y^{2d} & 0 \\
    -e_y^{2d} & e_x^{2d} & 0
  \end{bmatrix}
\]
The first row is the 2D model's normal. The second row is the edge tangent in
local 2D coordinates. The third row is the in-plane perpendicular that
completes a right-handed local pose.

\textbf{Subtle Details.}
The current vector form was chosen because the target reference frame is the
\texttt{TangentFrame}, not the world $xy$ plane. Projecting through world
vectors before taking dot products with $(u, v)$ handles rotated cameras,
tilted cameras, and arbitrary surface normals using the same code path. A
scalar world-angle formula throws away this reference-frame distinction and
implicitly assumes the output pose lives in the global $xy$ plane.

\textbf{Degenerate Projection.}
If the projected edge direction has near-zero length, the function falls back
to \texttt{tangent\_frame.basis\_u}. This is a defensive degeneracy fallback,
not meaningful edge evidence. A near-zero projection means the image-space
edge direction is effectively parallel to the surface normal, so it has no
stable tangent-plane orientation. The fallback prevents NaNs and keeps the
pose matrix well-formed, but it injects the current arbitrary local $u$
direction.

\textbf{CameraSM and General Reference Frames.}
The previous PR branch included a helper for projecting an image-space edge
angle into a 3D world tangent:
\begin{verbatim}
edge_angle_to_3d_tangent
\end{verbatim}
It was later removed when the 2D sensor path converged on:
\begin{verbatim}
_angle_to_pose_2d
\end{verbatim}
The removed helper remains a useful design reference for sensor modules that
want edge orientation but do not want the \texttt{TangentFrame} output
convention.

A general orientation projection helper should make the target reference
frame explicit. The reusable pattern is:
\begin{verbatim}
def image_angle_to_frame_vector(
    angle,
    world_camera,
    frame_u,
    frame_v,
    frame_normal,
):
    R = world_camera[:3, :3]
    image_x_world = R @ np.array([1.0, 0.0, 0.0])
    image_y_world = R @ np.array([0.0, -1.0, 0.0])

    feature_world = (
        np.cos(angle) * image_x_world
        + np.sin(angle) * image_y_world
    )
    feature_world = project_onto_tangent_plane(
        feature_world,
        frame_normal,
    )

    if np.linalg.norm(feature_world) < DEFAULT_TOLERANCE:
        return None

    feature_world = normalize(feature_world)
    return np.array([
        np.dot(feature_world, frame_u),
        np.dot(feature_world, frame_v),
    ])
\end{verbatim}
For \texttt{TwoDSensorModule}, the frame inputs come from the transported
\texttt{TangentFrame}. For \texttt{CameraSM}, they could instead be a
camera-aligned surface basis, a world-frame surface basis, or another
reference frame expected by the downstream learning module. The important
invariant is that the feature orientation is projected into the same reference
frame in which it will later be compared.

\textbf{Limitations.}
The function returns a 2D-local pose, not a world-frame pose. The normal row
is always $[0, 0, 1]$ because this pose is expressed in the 2D model's local
coordinates after projection into the tangent frame. Callers that need a
world-space tangent vector should use a separate helper rather than treating
this returned pose as a world-coordinate orientation.

\subsection{\texttt{TangentFrame}}

\textbf{The Problem.}
As the 2D sensor moves across a curved 3D surface, we need to express
sensor displacement in a consistent 2D coordinate frame. On a flat
surface a fixed $(u, v)$ pair suffices, but on a curved surface the
tangent plane rotates with the curvature. Naively accumulating
displacement vectors in a fixed world frame causes the tracked position
to drift off the surface.

\textbf{The Solution.}
\texttt{TangentFrame} maintains a right-handed orthonormal basis
$(u, v, n)$, where $n$ is the current surface normal, $u$ is the
horizontal tangent direction, and $v$ is the vertical tangent direction.
As the sensor moves to a new surface point, the method
\texttt{transport(new\_normal)} updates the basis via
\emph{parallel transport}---the unique minimum-rotation update that
keeps $u$ and $v$ in the new tangent plane without introducing
extraneous twist. This is the discrete analogue of parallel-transporting
a vector along a geodesic on a Riemannian manifold
(\texttt{https://en.wikipedia.org/wiki/Parallel\_transport}).

\textbf{Initialization.}
Given an initial surface normal $n$, the constructor builds $u$ and $v$
as follows. It picks an arbitrary reference axis $a = [0, 1, 0]$,
falling back to $a = [0, 0, 1]$ if $n$ is nearly parallel to $a$
($|\cos\theta| > 1 - \epsilon$). Then:
\begin{align*}
  u &= \mathrm{normalize}(a \times n) \\
  v &= \mathrm{normalize}(n \times u)
\end{align*}
The cross products ensure $u$ lies in the tangent plane and $(u, v, n)$
forms a right-handed frame.

\begin{figure}[h]
  \centering
  \includegraphics[width=0.8\textwidth]{../imgs/tangent_frame_init.png}
  \caption{Initialization of the orthonormal tangent frame $(u, v, n)$ from a surface normal $n$.}
\end{figure}

\textbf{Parallel Transport.}
When \texttt{transport(new\_normal)} is called with a new surface normal
$n'$, the update proceeds in three steps:
\begin{enumerate}
  \item Compute the rotation $R$ that maps $n \to n'$ via the
    axis-angle representation:
    \[
      \text{axis} = \mathrm{normalize}(n \times n'), \quad
      \theta = \arccos(\mathrm{clip}(n \cdot n', -1, 1))
    \]
  \item Apply $R$ to $u$: this keeps $u$ as close as possible to its
    previous direction while moving it into the new tangent plane.
  \item Re-orthonormalize to suppress floating-point drift accumulated
    over many steps:
    \[
      u \leftarrow \mathrm{normalize}(u - (u \cdot n') \, n'),
      \quad v \leftarrow n' \times u
    \]
\end{enumerate}
Step 3 is necessary because repeated small rotations accumulate
numerical error; projecting $u$ back onto the tangent plane and
recomputing $v$ from scratch keeps the frame exactly orthonormal.

\begin{figure}[h]
  \centering
  \includegraphics[width=0.6\textwidth]{../imgs/tangent_frame_transport.png}
  \caption{Parallel transport of the tangent frame from normal $n$ to a new normal $n'$.}
\end{figure}

\subsection{\texttt{arc\_from\_projection} and Arc-Length Correction}

\textbf{The Problem.}
When the sensor moves along a curved surface, the displacement we observe is a
chord in the tangent plane, not the true distance traveled along the curve.
On a convex surface the sensor must travel further than the straight-line
projection suggests; without correction, accumulated 2D positions are
systematically compressed relative to the actual surface path.

\textbf{The Solution.}
At each surface point we fit an \emph{osculating circle}: the unique circle
that is tangent to the surface and has the same normal curvature $k$ in the
direction of movement. The osculating circle is the best local circular
approximation to the curve, in the sense that it agrees with the curve up to
second order. The approximation holds well when curvature is approximately
constant over the displacement, but becomes inaccurate for surfaces with
rapidly varying curvature (e.g., a sharp ridge crossed in a single large step).

Under this assumption the relationship between tangent-plane chord $p$ and
arc length $s$ is:
\[
  p = \frac{\sin(k \cdot s)}{k}
  \quad\Longrightarrow\quad
  s = \frac{\arcsin(k \cdot p)}{k}
\]
This is implemented in \texttt{arc\_from\_projection(tangent\_projection, curvature)}.
Two guard conditions keep the formula numerically safe:
\begin{itemize}
  \item $|k \cdot p| < 0.001$: the surface is nearly flat over the step, so
        $\arcsin(k p) \approx k p$ and no correction is applied.
  \item $|k \cdot p| \geq 1.0$: the chord exceeds the radius of curvature,
        meaning the sensor has moved past the most extreme visible point under
        the constant-curvature assumption. The correction is skipped and a
        warning is logged; the proper remedy is a policy that takes smaller 3D
        steps.
\end{itemize}
The formula is sign-preserving (\texttt{np.copysign}) and works for both
convex ($k > 0$) and concave ($k < 0$) surfaces because the arc-to-chord
geometry on a circle is the same regardless of the sign of curvature.

\textbf{Helper: \texttt{directional\_curvature}.}
Before correcting displacement we need the normal curvature $k$ in the
direction of movement. Given principal curvatures $k_1, k_2$ and their
directions $\hat{d}_1, \hat{d}_2$, Euler's curvature formula gives:
\[
  k(\theta) = k_1 \cos^2\theta + k_2 \sin^2\theta
\]
where $\theta$ is the angle between the movement direction and $\hat{d}_1$.
\texttt{directional\_curvature} validates that $\hat{d}_1$ and $\hat{d}_2$
are orthonormal and that the movement direction lies in their span before
applying this formula.

\textbf{Helper: \texttt{arc\_length\_corrected\_displacement}.}
This function ties the two helpers together. Given tangent-frame displacements
$(du, dv)$ along basis vectors $(u, v)$, it:
\begin{enumerate}
  \item Calls \texttt{directional\_curvature} once for $u$ and once for $v$
        to obtain $k_u$ and $k_v$ from the observed principal curvatures and
        their pose vectors.
  \item Passes each chord-displacement through \texttt{arc\_from\_projection}
        to obtain arc-length-corrected displacements $(\hat{u}, \hat{v})$.
\end{enumerate}
The result is a pair of corrected 2D displacements that accurately reflect the
distance the sensor traveled along the surface in each tangent direction.

\section{Putting it Together in TwoDSensorModule}

The previous sections described edge extraction, tangent-frame transport, and
arc-length correction as separate pieces. In the runtime implementation these
pieces meet inside \texttt{TwoDSensorModule.step}. The method starts from the
same raw-observation contract as a standard sensor module, but it changes the
meaning of the outgoing message: the location and displacement are 2D
coordinates embedded in a 3D-shaped Monty message, and an accepted texture
edge is the only feature that makes the outgoing pose fully defined.

\subsection{Runtime Flow in \texttt{step}}

\textbf{What it does.}
\texttt{step(ctx, observation, motor\_only\_step=False)} converts a raw sensor
observation into a Monty message whose features remain compatible with the
standard sensor-module API while its movement fields describe accumulated
2D travel over the surface. It preserves the 3D curvature information needed
for movement correction, optionally replaces the outgoing pose with a
texture-edge pose, then rewrites the outgoing location and displacement into
the 2D coordinate convention.

\textbf{Algorithm.}
\begin{enumerate}
  \item If raw-observation logging is enabled, save the raw observation
        together with the current sensor rotation and position before any
        feature processing mutates the message state.
  \item Run \texttt{ObservationProcessor.process(observation)}. This produces
        the usual 3D surface state: location, on-object status, surface normal,
        principal curvatures, curvature-derived pose vectors, and any requested
        non-morphological features.
  \item Copy the current pose vectors into
        \texttt{curvature\_pose\_vectors}, and copy the current surface normal
        into \texttt{true\_surface\_normal}. These copies happen before edge
        extraction because edge extraction can overwrite the
        \texttt{pose\_vectors} morphological feature.
  \item Set the \texttt{pose\_fully\_defined} morphological flag to
        \texttt{False}. Curvature directions no longer count as a fully defined
        pose for this sensor module; only an accepted texture edge can restore
        the flag to \texttt{True}.
  \item If the state is usable and the center is on object, update the
        transported \texttt{TangentFrame} from the saved surface normal. The
        first on-object observation initializes the frame; later on-object
        observations transport the same frame instance to the new normal.
  \item If edge features were requested, call \texttt{\_extract\_2d\_edge}.
        A detected texture edge replaces the outgoing pose vectors with a
        2D-local edge pose and writes \texttt{edge\_strength} or
        \texttt{coherence} when those features were requested. No-edge and
        geometric-edge cases leave the curvature-derived pose vectors in the
        message but keep \texttt{pose\_fully\_defined=False}.
  \item Apply configured message noise while \texttt{use\_state} is still
        true. If \texttt{motor\_only\_step} is set, force
        \texttt{use\_state=False} so the message is not passed to a learning
        module as a percept.
  \item Call the 2D position update with the saved curvature pose and saved
        surface normal. This projects the 3D movement into the tangent frame,
        applies arc-length correction when curvature data is available, and
        emits \texttt{location} and \texttt{displacement} as
        \([x_{2d}, y_{2d}, 0]\).
  \item Run the percept filter last. With the default
        \texttt{PassthroughPerceptFilter}, this is a no-op; with a
        \texttt{FeatureChangeFilter}, the comparison sees the final 2D message
        rather than the intermediate 3D surface state.
\end{enumerate}

\textbf{Gotchas.}
The saved \texttt{curvature\_pose\_vectors} and
\texttt{true\_surface\_normal} are not redundant local variables. They preserve
the original 3D surface geometry after edge extraction has had a chance to
replace the outgoing pose. Arc-length correction needs the curvature frame
that came from \texttt{ObservationProcessor}; using the edge pose instead would
feed a texture tangent into a geometric curvature calculation and produce
incorrect corrected displacements.

\textbf{Subtle Details.}
\texttt{pose\_fully\_defined} is reset before edge extraction because the
standard observation processor can mark a curvature-derived 3D pose as fully
defined, but \texttt{TwoDSensorModule} uses a narrower contract: the pose is
fully defined only when a texture edge provides the in-plane direction. This
keeps the downstream learning module from treating ordinary principal
curvature directions as semantic 2D edge orientations.

The tangent frame is updated before edge extraction so
\texttt{\_angle\_to\_pose\_2d} can express the image-space edge angle in the
current transported 2D frame. The frame is also updated before the 2D movement
rewrite, so the same basis is used for pose conversion and displacement
projection during the step.

\textbf{Limitations.}
The outgoing message keeps shape \((3,)\) for compatibility, but after
the 2D position update the third coordinate is a dummy value fixed at zero. The
first on-object observation seeds the 2D location from world \(x, y\), not from
an object-intrinsic origin. As a result, two episodes that begin at different
points on the same object produce 2D coordinate traces that are translated by
their starting world \(x, y\), and their axes depend on the arbitrary initial
\texttt{TangentFrame} basis.

\textbf{Alternatives Considered.}
The obvious alternative is to run edge extraction first and then use the final
message pose everywhere. That would make the message simpler, but it would
collapse two different pose meanings into one field: texture-edge pose for the
learning module and curvature pose for surface-distance correction. The current
save-before-overwrite sequence keeps those contracts separate while preserving
the existing Monty message schema.
