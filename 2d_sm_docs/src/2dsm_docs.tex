\section{Introduction}

This document is a reference manual for
\href{https://github.com/thousandbrainsproject/tbp.monty}{\texttt{TwoDSensorModule}}
as implemented in \texttt{tbp.monty} version \texttt{0.33.0}. It is written
for future maintainers and contributors who need to improve the 2D sensor
module without losing the design intent behind the current implementation. The
goal is to explain what problem each algorithm solves, why the main choices
were made, what limitations remain, and where future work can build on the
existing design.

\texttt{TwoDSensorModule} converts local surface observations into a
2D-compatible representation while preserving compatibility with Monty's
message interface. It has two central responsibilities. First, it detects the
dominant texture-edge orientation in an image patch so a local visual edge can
be represented as pose information. Second, it accumulates movement over a
curved surface in a transported 2D surface chart while still emitting
3D-shaped location and displacement fields.

The implementation of \texttt{TwoDSensorModule} is divided into two main
parts:

\begin{enumerate}
  \item Estimating dominant texture-edge orientation in a sensor patch.
  \item Accumulating 2D movement over a curved surface.
\end{enumerate}

\section{Detecting Dominant Texture-Edge Orientation in a Patch}
\label{edge_detection}

The goal of the edge-detection work was to detect the dominant texture-edge orientation in an image patch.
Once detected, the edge orientation is projected into the 2D tangent frame used by \texttt{TwoDSensorModule} (see Section~\ref{sec:tangent_frame}).
Unlike some other features in Monty, which are read directly from the center pixel of a $64 \times 64$ patch, we wanted to extract the dominant orientation across the \textit{whole} patch.
This led to the development of \texttt{EdgeDetector} (in \texttt{edge\_detection.py}), which extracts an edge angle between $(0, \pi]$ when a dominant edge is identified, along with supporting edge attributes.
The Edge Detection module also provides a helper for projecting the detected image-space edge angle into the vectors expected by the chosen reference frame.

\subsection{Patch-Level Edge Detection Pipeline}

In computer vision, one common way to detect an edge at the pixel level is to analyze changes in image gradients along the $x$- and $y$-directions.
The Canny edge detector is an example of this kind of gradient-based method~\cite{opencv_canny}.

To aggregate gradient information across a whole patch, we use the structure tensor, a compact summary of local gradient variation~\cite{khan_corner_detection,opencv_gst}.
The structure tensor lets us aggregate gradient evidence across pixels in a controlled way instead of relying on a single center-pixel gradient.

% TODO: A small figure showing how edge angle is measured (image-x to image-y).

The following describes the main algorithm implemented in \texttt{EdgeDetector}.
Given a \texttt{SensorObservation}, the detector first extracts the $(64, 64, 3)$ RGB patch and converts it to grayscale.
The current Monty implementation stores \texttt{observation["rgba"]} in red-green-blue order, but users should be careful if they are using an alternate approach such as constructing images via OpenCV, as OpenCV's \texttt{cv2.imread} returns blue-green-red (BGR) images.
Passing BGR data into \texttt{cv2.COLOR\_RGB2GRAY} changes the grayscale values that drive the gradient calculation.

From the grayscale image, the \texttt{EdgeDetector} computes Sobel gradients $I_x$ (gradient in the $x$-direction) and $I_y$ (gradient in the $y$-direction).
From these gradients, we can build a structure tensor for each pixel of our $64 \times 64$ patch as follows:
\[
  J =
  \begin{bmatrix}
    I_x^2 & I_x I_y \\
    I_x I_y & I_y^2
  \end{bmatrix}
\]

The per-pixel structure tensors are then reduced to a single aggregated $2 \times 2$ matrix for the entire patch using a center-biased weighted average, as Monty generally extracts features near the center of a sensor patch.
The weight for each pixel is calculated as the product of Gaussian radial weighting (which gives more importance to center pixels) and gradient energy (which gives more importance to clear, strong edges).

From the aggregated structure tensor, the dominant gradient angle follows the standard half-angle relation, evaluated with the two-argument arctangent so the quadrant is preserved:
\[
  \theta_\text{gradient} =
    \frac{1}{2}
    \operatorname{atan2}(2J_{xy}, J_{xx} - J_{yy})
\]
Equivalently, this is the quadrant-aware form of applying $\arctan$ to $2J_{xy} / (J_{xx} - J_{yy})$.
The edge angle is perpendicular to this gradient direction:
\[
  \theta_\text{edge} = \theta_g + \frac{\pi}{2}
\]
In practice the detected edge orientation is undirected: angles that differ by $\pi$ describe the same edge line.
For horizontal lines, the practical endpoint convention resolves to $\pi$ rather than $0$ because NumPy's \texttt{arctan2(+0.0, negative)} returns $\pi$ under IEEE 754 signed-zero behavior~\cite{numpy_arctan2}.
The first argument is \texttt{+0.0} because an ideal horizontal line has no horizontal-gradient component, so the cross term $J_{xy}=I_x I_y$ aggregates to zero; the second argument is negative because vertical gradient energy dominates, making $J_{xx} - J_{yy} < 0$.

The aggregated tensor is a positive semi-definite matrix with two eigenvalues, $\lambda_{\min}$ and $\lambda_{\max}$, where $\lambda_{\min}, \lambda_{\max} \geq 0$.
The eigenvectors of the aggregated tensor identify the directions of smallest and largest gradient variation: $\lambda_{\max}$ measures gradient energy in the dominant gradient direction, while $\lambda_{\min}$ measures gradient energy in the orthogonal direction.
A clean straight edge has one large eigenvalue and one small eigenvalue; a corner, junction, or isotropic texture has two more similar eigenvalues because gradient energy exists in multiple directions.
Edge strength is defined as $\sqrt{\lambda_{\max}}$.
Its mathematical range is $[0, \infty)$, but in this detector it is finite because the inputs are finite grayscale Sobel gradients that are smoothed and averaged with finite weights; in current experiments, useful values were roughly in the $0$--$4$ range.
Coherence is defined as:
$
  \frac{\lambda_{\max} - \lambda_{\min}}
       {\lambda_{\max} + \lambda_{\min}}
$.
For positive semi-definite tensors, coherence is bounded in $[0, 1]$.

Coherence measures how concentrated the gradient evidence is around one orientation: values near $1$ indicate a clean single edge, while values near $0$ indicate isotropic texture, corners, junctions, or other competing directions.
The final boolean \texttt{has\_edge} is true only when edge strength exceeds \texttt{strength\_threshold} and coherence exceeds \texttt{coherence\_threshold}.

\textbf{Center Bias and \texttt{max\_center\_offset}.}
Radial weighting and \texttt{max\_center\_offset} solve different problems.
Radial weighting is continuous and always participates in the orientation estimate: it downweights gradients far from the center but still allows a strong off-center edge to influence the aggregate.
By contrast, \texttt{max\_center\_offset} is an optional hard rejection rule.
Once an orientation has been estimated, the detector projects the weighted gradient evidence onto the detected edge normal and computes how far the weighted edge centerline is from the patch center.
If that distance is larger than \texttt{max\_center\_offset}, the detector returns no edge.

The default value is \texttt{None}, so this hard center check is disabled.
The option is mainly useful for reducing extra edge clutter during visualization.
It does not replace radial weighting, because it operates after the dominant orientation has already been estimated.

\textbf{Geometric Edge Check.}
\texttt{EdgeDetector} also checks whether the detected RGB edge corresponds to a depth discontinuity.
It computes Sobel gradients on the depth patch, takes the depth gradient at the center pixel, and projects that gradient onto the direction perpendicular to the RGB edge.
If this perpendicular depth gradient exceeds \texttt{depth\_edge\_threshold}, the edge is marked as a geometric edge.

% TODO: Add diagram / sketch of how geometric edge check works. 

This matters because \texttt{TwoDSensorModule} is interested in texture edges on a 2D surface, such as the edge of a logo on a mug, not object boundaries or surface creases.
\texttt{EdgeDetector} only reports \texttt{is\_geometric\_edge}; the filtering decision happens in \texttt{TwoDSensorModule.\_extract\_2d\_edge}.
The default \texttt{depth\_edge\_threshold} is \texttt{0.01}, which corresponds to about one centimeter when depth is measured in meters.

\textbf{Parameter Choices and Limitations.}
Several defaults are pragmatic rather than analytically derived.
\texttt{kernel\_size=7} is a remnant from an earlier version that focused on edges in a small center region.
\texttt{radius=14.0} was chosen as a reasonable center neighborhood for a $64 \times 64$ patch.
\texttt{sigma\_r=7.0} controls the radial Gaussian falloff, but its exact value has not been justified independently.
\texttt{coherence\_threshold=0.5} is a middle-of-range requirement on a score bounded between 0 and 1.
\texttt{strength\_threshold=0.1} is intentionally low so weak but coherent texture edges are still detected.

The detector returns one dominant orientation.
It cannot represent two edges, a corner, a junction, or repeated strokes in the same patch except by reducing coherence or producing a compromise orientation.
The geometric edge check is also center-pixel based: it computes the full depth gradient image but samples only the center depth gradient for classification.
A noisy center depth value can therefore mark a texture edge as geometric, or miss a depth discontinuity that is nearby but not centered.

\textbf{Alternatives.}
We explored well-known edge detection methods such as Canny edge detection, but Canny returns an edge-pixel mask rather than a compact dominant orientation, strength, and coherence for a patch.
A single-pixel Sobel angle at the patch center would be closer to the old center-feature interpretation, but it is brittle when the edge is slightly off center or noisy at the exact center.
A Gabor filter bank could test for edges at several orientations, but it requires choosing a discrete orientation grid and running multiple convolutions.
The structure tensor gives a continuous orientation estimate in one pass while still allowing center bias through the weight map.

\subsection{Detector Output and Downstream Contract}

\textbf{The Problem.}
The edge detector produces several related quantities, and downstream code needs to distinguish measurement from decision.
A patch can contain enough gradient evidence to estimate an orientation but still fail the detector's thresholds because the edge is too weak or the gradient evidence is not coherent enough.
Conversely, a patch can fail before an orientation exists at all, such as a uniform patch or an edge rejected by \texttt{max\_center\_offset}.

\textbf{The Solution.}
\texttt{EdgeFeatures} is the handoff object returned by \texttt{EdgeDetector.\_\_call\_\_}.
It stores:
\begin{itemize}
  \item \texttt{angle}: the estimated dominant edge orientation, or \texttt{None} when no reliable orientation was computed.
  \item \texttt{strength}: the dominant gradient magnitude scale.
  \item \texttt{coherence}: the orientation-quality score in $[0, 1]$.
  \item \texttt{is\_geometric\_edge}: whether the RGB edge corresponds to a depth discontinuity.
  \item \texttt{has\_edge}: the final thresholded detector decision.
\end{itemize}
\texttt{has\_edge} is the definitive decision flag.
\texttt{angle} is an estimated dominant orientation whenever the detector has enough gradient evidence to compute one.
A weak or low-coherence patch can therefore have a non-\texttt{None} \texttt{angle} while \texttt{has\_edge} is false.

\textbf{Downstream Contract.}
\texttt{TwoDSensorModule.\_extract\_2d\_edge} uses \texttt{has\_edge} as the first gate.
If \texttt{has\_edge} is false, the original curvature-based pose is left unchanged.
If \texttt{has\_edge} is true but \texttt{is\_geometric\_edge} is also true, the pose is also left unchanged, because the 2D sensor is trying to represent texture edges on a surface rather than object boundaries or surface creases.
Only a detected non-geometric edge is converted into 2D pose vectors.

\textbf{Gotchas.}
\texttt{angle is not None} is not equivalent to \texttt{has\_edge}.
Treating a non-\texttt{None} angle as a detected edge admits weak or incoherent patches into the 2D pose pipeline.
Treating \texttt{has\_edge} as the gate preserves the detector's intended separation between diagnostic measurements and usable edge features.

% Comment: The below limitation is not an issue, remove. 
\textbf{Limitations.}
The dataclass does not encode why detection failed.
A uniform patch and an edge rejected by \texttt{max\_center\_offset} both return
\begin{itemize}
  \item \texttt{angle=None}
  \item \texttt{strength=0.0}
  \item \texttt{coherence=0.0}
  \item \texttt{is\_geometric\_edge=False}
  \item \texttt{has\_edge=False}
\end{itemize}
If future debugging or learning logic needs to distinguish these cases, the result type will need an explicit rejection reason.

\subsection{Projecting Image-Space Edge Orientation into 2D Pose}

\textbf{The Problem.}
\texttt{EdgeDetector} is intentionally reusable.
It can detect a dominant edge orientation for \texttt{TwoDSensorModule}, \texttt{CameraSM}, or any other sensor module that wants an image-space edge feature.
The detected angle by itself is still viewpoint-dependent: it is measured from the image x-axis toward the image y-axis, i.e., downward in the image.
A sensor module must decide which reference frame should receive that orientation.

\texttt{\_angle\_to\_pose\_2d} is specifically the adapter for \texttt{TwoDSensorModule}.
It converts an image-space edge angle into pose vectors expressed in the transported \texttt{TangentFrame}.
This is different from the earlier \texttt{edge\_angle\_to\_2d\_pose} formulation, which used a scalar \texttt{world\_angle = ref - theta} and produced pose vectors in the world $xy$ plane.
That older path was useful for a flat world-XY interpretation, but it was not the correct reference frame for the 2D sensor moving over a curved surface.

\textbf{The Solution.}
The current function keeps the reference-frame conversion explicit.
It first maps the image axes into world coordinates:
\[
  x_{\mathrm{img}}^{w} = R[1, 0, 0]^T,
  \quad
  y_{\mathrm{img}}^{w} = R[0, -1, 0]^T
\]
where $R$ is the rotation component of \texttt{world\_camera}.
The negative sign in the image-y basis is load-bearing: image coordinates have positive y downward, while the camera/world convention used here treats positive y in the opposite direction.

The image-space edge angle is then converted into a world-space direction:
\[
  e^w =
    \cos(\theta) x_{\mathrm{img}}^{w}
    + \sin(\theta) y_{\mathrm{img}}^{w}
\]
This vector is projected onto the local surface tangent plane and normalized.
Finally, it is expressed in the transported tangent basis:
\[
  e^{2d} =
  \begin{bmatrix}
    e^w \cdot u \\
    e^w \cdot v \\
    0
  \end{bmatrix}
\]
where $u$ and $v$ are \texttt{tangent\_frame.basis\_u} and \texttt{tangent\_frame.basis\_v}.
The returned pose vectors are:
\[
  \begin{bmatrix}
    0 & 0 & 1 \\
    e_x^{2d} & e_y^{2d} & 0 \\
    -e_y^{2d} & e_x^{2d} & 0
  \end{bmatrix}
\]
The first row is the 2D model's normal.
The second row is the edge tangent in local 2D coordinates.
The third row is the in-plane perpendicular that completes a right-handed local pose.

\textbf{Subtle Details.}
The current vector form was chosen because the target reference frame is the \texttt{TangentFrame}, not the world $xy$ plane.
Projecting through world vectors before taking dot products with $(u, v)$ handles rotated cameras, tilted cameras, and arbitrary surface normals using the same code path.
A scalar world-angle formula throws away this reference-frame distinction and implicitly assumes the output pose lives in the global $xy$ plane.

\textbf{Degenerate Projection.}
If the projected edge direction has near-zero length, the function falls back to \texttt{tangent\_frame.basis\_u}.
This is a defensive degeneracy fallback, not meaningful edge evidence.
A near-zero projection means the image-space edge direction is effectively parallel to the surface normal, so it has no stable tangent-plane orientation.
The fallback prevents NaNs and keeps the pose matrix well-formed, but it injects the current arbitrary local $u$ direction.

\textbf{CameraSM and General Reference Frames.}
The previous PR branch included a helper for projecting an image-space edge angle into a 3D world tangent:
\begin{verbatim}
edge_angle_to_3d_tangent
\end{verbatim}
It was later removed when the 2D sensor path converged on:
\begin{verbatim}
_angle_to_pose_2d
\end{verbatim}
The removed helper remains a useful design reference for sensor modules that want edge orientation but do not want the \texttt{TangentFrame} output convention.

A general orientation projection helper should make the target reference frame explicit.
The reusable pattern is:

% Comment: Question - can this work for any dimension? 
\begin{verbatim}
def image_angle_to_frame_vector(
    angle,
    world_camera,
    frame_u,
    frame_v,
    frame_normal,
):
    R = world_camera[:3, :3]
    image_x_world = R @ np.array([1.0, 0.0, 0.0])
    image_y_world = R @ np.array([0.0, -1.0, 0.0])

    feature_world = (
        np.cos(angle) * image_x_world
        + np.sin(angle) * image_y_world
    )
    feature_world = project_onto_tangent_plane(
        feature_world,
        frame_normal,
    )

    if np.linalg.norm(feature_world) < DEFAULT_TOLERANCE:
        return None

    feature_world = normalize(feature_world)
    return np.array([
        np.dot(feature_world, frame_u),
        np.dot(feature_world, frame_v),
    ])
\end{verbatim}
For \texttt{TwoDSensorModule}, the frame inputs come from the transported \texttt{TangentFrame}.
For \texttt{CameraSM}, they could instead be a camera-aligned surface basis, a world-frame surface basis, or another reference frame expected by the downstream learning module.
The important invariant is that the feature orientation is projected into the same reference frame in which it will later be compared.

\textbf{Limitations.}
The function returns a 2D-local pose, not a world-frame pose.
The normal row is always $[0, 0, 1]$ because this pose is expressed in the 2D model's local coordinates after projection into the tangent frame.
Callers that need a world-space tangent vector should use a separate helper rather than treating this returned pose as a world-coordinate orientation.

\subsection{\texttt{TangentFrame}}
\label{sec:tangent_frame}

\textbf{The Problem.}
As the 2D sensor moves across a curved 3D surface, we need to express
sensor displacement in a consistent 2D coordinate frame. On a flat
surface a fixed $(u, v)$ pair suffices, but on a curved surface the
tangent plane rotates with the curvature. Naively accumulating
displacement vectors in a fixed world frame causes the tracked position
to drift off the surface.

\textbf{The Solution.}
\texttt{TangentFrame} maintains a right-handed orthonormal basis
$(u, v, n)$, where $n$ is the current surface normal, $u$ is the
horizontal tangent direction, and $v$ is the vertical tangent direction.
As the sensor moves to a new surface point, the method
\texttt{transport(new\_normal)} updates the basis via
\emph{parallel transport}---the unique minimum-rotation update that
keeps $u$ and $v$ in the new tangent plane without introducing
extraneous twist. This is the discrete analogue of parallel-transporting
a vector along a geodesic on a Riemannian manifold
(\texttt{https://en.wikipedia.org/wiki/Parallel\_transport}).

\textbf{Initialization.}
Given an initial surface normal $n$, the constructor builds $u$ and $v$
as follows. It picks an arbitrary reference axis $a = [0, 1, 0]$,
falling back to $a = [0, 0, 1]$ if $n$ is nearly parallel to $a$
($|\cos\theta| > 1 - \epsilon$). Then:
\begin{align*}
  u &= \mathrm{normalize}(a \times n) \\
  v &= \mathrm{normalize}(n \times u)
\end{align*}
The cross products ensure $u$ lies in the tangent plane and $(u, v, n)$
forms a right-handed frame.

\begin{figure}[h]
  \centering
  \includegraphics[width=0.8\textwidth]{../imgs/tangent_frame_init.png}
  \caption{Initialization of the orthonormal tangent frame $(u, v, n)$ from a surface normal $n$.}
\end{figure}

\textbf{Parallel Transport.}
When \texttt{transport(new\_normal)} is called with a new surface normal
$n'$, the update proceeds in three steps:
\begin{enumerate}
  \item Compute the rotation $R$ that maps $n \to n'$ via the
    axis-angle representation:
    \[
      \text{axis} = \mathrm{normalize}(n \times n'), \quad
      \theta = \arccos(\mathrm{clip}(n \cdot n', -1, 1))
    \]
  \item Apply $R$ to $u$: this keeps $u$ as close as possible to its
    previous direction while moving it into the new tangent plane.
  \item Re-orthonormalize to suppress floating-point drift accumulated
    over many steps:
    \[
      u \leftarrow \mathrm{normalize}(u - (u \cdot n') \, n'),
      \quad v \leftarrow n' \times u
    \]
\end{enumerate}
Step 3 is necessary because repeated small rotations accumulate
numerical error; projecting $u$ back onto the tangent plane and
recomputing $v$ from scratch keeps the frame exactly orthonormal.

\begin{figure}[h]
  \centering
  \includegraphics[width=0.6\textwidth]{../imgs/tangent_frame_transport.png}
  \caption{Parallel transport of the tangent frame from normal $n$ to a new normal $n'$.}
\end{figure}

\subsection{\texttt{arc\_from\_projection} and Arc-Length Correction}

\textbf{The Problem.}
When the sensor moves along a curved surface, the displacement we observe is a
chord in the tangent plane, not the true distance traveled along the curve.
On a convex surface the sensor must travel further than the straight-line
projection suggests; without correction, accumulated 2D positions are
systematically compressed relative to the actual surface path.

\textbf{The Solution.}
At each surface point we fit an \emph{osculating circle}: the unique circle
that is tangent to the surface and has the same normal curvature $k$ in the
direction of movement. The osculating circle is the best local circular
approximation to the curve, in the sense that it agrees with the curve up to
second order. The approximation holds well when curvature is approximately
constant over the displacement, but becomes inaccurate for surfaces with
rapidly varying curvature (e.g., a sharp ridge crossed in a single large step).

Under this assumption the relationship between tangent-plane chord $p$ and
arc length $s$ is:
\[
  p = \frac{\sin(k \cdot s)}{k}
  \quad\Longrightarrow\quad
  s = \frac{\arcsin(k \cdot p)}{k}
\]
This is implemented in \texttt{arc\_from\_projection(tangent\_projection, curvature)}.
Two guard conditions keep the formula numerically safe:
\begin{itemize}
  \item $|k \cdot p| < 0.001$: the surface is nearly flat over the step, so
        $\arcsin(k p) \approx k p$ and no correction is applied.
  \item $|k \cdot p| \geq 1.0$: the chord exceeds the radius of curvature,
        meaning the sensor has moved past the most extreme visible point under
        the constant-curvature assumption. The correction is skipped and a
        warning is logged; the proper remedy is a policy that takes smaller 3D
        steps.
\end{itemize}
The formula is sign-preserving (\texttt{np.copysign}) and works for both
convex ($k > 0$) and concave ($k < 0$) surfaces because the arc-to-chord
geometry on a circle is the same regardless of the sign of curvature.

\textbf{Helper: \texttt{directional\_curvature}.}
Before correcting displacement we need the normal curvature $k$ in the
direction of movement. Given principal curvatures $k_1, k_2$ and their
directions $\hat{d}_1, \hat{d}_2$, Euler's curvature formula gives:
\[
  k(\theta) = k_1 \cos^2\theta + k_2 \sin^2\theta
\]
where $\theta$ is the angle between the movement direction and $\hat{d}_1$.
\texttt{directional\_curvature} validates that $\hat{d}_1$ and $\hat{d}_2$
are orthonormal and that the movement direction lies in their span before
applying this formula.

\textbf{Helper: \texttt{arc\_length\_corrected\_displacement}.}
This function ties the two helpers together. Given tangent-frame displacements
$(du, dv)$ along basis vectors $(u, v)$, it:
\begin{enumerate}
  \item Calls \texttt{directional\_curvature} once for $u$ and once for $v$
        to obtain $k_u$ and $k_v$ from the observed principal curvatures and
        their pose vectors.
  \item Passes each chord-displacement through \texttt{arc\_from\_projection}
        to obtain arc-length-corrected displacements $(\hat{u}, \hat{v})$.
\end{enumerate}
The result is a pair of corrected 2D displacements that accurately reflect the
distance the sensor traveled along the surface in each tangent direction.

\section{Putting it Together in TwoDSensorModule}

The previous sections described edge extraction, tangent-frame transport, and
arc-length correction as separate pieces. In the runtime implementation these
pieces meet inside \texttt{TwoDSensorModule.step}. The method starts from the
same raw-observation contract as a standard sensor module, but it changes the
meaning of the outgoing message: the location and displacement are 2D
coordinates embedded in a 3D-shaped Monty message, and an accepted texture
edge is the only feature that makes the outgoing pose fully defined.

\subsection{Runtime Flow in \texttt{step}}

\textbf{What it does.}
\texttt{step(ctx, observation, motor\_only\_step=False)} converts a raw sensor
observation into a Monty message whose features remain compatible with the
standard sensor-module API while its movement fields describe accumulated
2D travel over the surface. It preserves the 3D curvature information needed
for movement correction, optionally replaces the outgoing pose with a
texture-edge pose, then rewrites the outgoing location and displacement into
the 2D coordinate convention.

\textbf{Algorithm.}
\begin{enumerate}
  \item If raw-observation logging is enabled, save the raw observation
        together with the current sensor rotation and position before any
        feature processing mutates the message state.
  \item Run \texttt{ObservationProcessor.process(observation)}. This produces
        the usual 3D surface state: location, on-object status, surface normal,
        principal curvatures, curvature-derived pose vectors, and any requested
        non-morphological features.
  \item Copy the current pose vectors into
        \texttt{curvature\_pose\_vectors}, and copy the current surface normal
        into \texttt{true\_surface\_normal}. These copies happen before edge
        extraction because edge extraction can overwrite the
        \texttt{pose\_vectors} morphological feature.
  \item Set the \texttt{pose\_fully\_defined} morphological flag to
        \texttt{False}. Curvature directions no longer count as a fully defined
        pose for this sensor module; only an accepted texture edge can restore
        the flag to \texttt{True}.
  \item If the state is usable and the center is on object, update the
        transported \texttt{TangentFrame} from the saved surface normal. The
        first on-object observation initializes the frame; later on-object
        observations transport the same frame instance to the new normal.
  \item If edge features were requested, call \texttt{\_extract\_2d\_edge}.
        A detected texture edge replaces the outgoing pose vectors with a
        2D-local edge pose and writes \texttt{edge\_strength} or
        \texttt{coherence} when those features were requested. No-edge and
        geometric-edge cases leave the curvature-derived pose vectors in the
        message but keep \texttt{pose\_fully\_defined=False}.
  \item Apply configured message noise while \texttt{use\_state} is still
        true. If \texttt{motor\_only\_step} is set, force
        \texttt{use\_state=False} so the message is not passed to a learning
        module as a percept.
  \item Call the 2D position update with the saved curvature pose and saved
        surface normal. This projects the 3D movement into the tangent frame,
        applies arc-length correction when curvature data is available, and
        emits \texttt{location} and \texttt{displacement} as
        \([x_{2d}, y_{2d}, 0]\).
  \item Run the percept filter last. With the default
        \texttt{PassthroughPerceptFilter}, this is a no-op; with a
        \texttt{FeatureChangeFilter}, the comparison sees the final 2D message
        rather than the intermediate 3D surface state.
\end{enumerate}

\textbf{Gotchas.}
The saved \texttt{curvature\_pose\_vectors} and
\texttt{true\_surface\_normal} are not redundant local variables. They preserve
the original 3D surface geometry after edge extraction has had a chance to
replace the outgoing pose. Arc-length correction needs the curvature frame
that came from \texttt{ObservationProcessor}; using the edge pose instead would
feed a texture tangent into a geometric curvature calculation and produce
incorrect corrected displacements.

\textbf{Subtle Details.}
\texttt{pose\_fully\_defined} is reset before edge extraction because the
standard observation processor can mark a curvature-derived 3D pose as fully
defined, but \texttt{TwoDSensorModule} uses a narrower contract: the pose is
fully defined only when a texture edge provides the in-plane direction. This
keeps the downstream learning module from treating ordinary principal
curvature directions as semantic 2D edge orientations.

The tangent frame is updated before edge extraction so
\texttt{\_angle\_to\_pose\_2d} can express the image-space edge angle in the
current transported 2D frame. The frame is also updated before the 2D movement
rewrite, so the same basis is used for pose conversion and displacement
projection during the step.

\textbf{Limitations.}
The outgoing message keeps shape \((3,)\) for compatibility, but after
the 2D position update the third coordinate is a dummy value fixed at zero. The
first on-object observation seeds the 2D location from world \(x, y\), not from
an object-intrinsic origin. As a result, two episodes that begin at different
points on the same object produce 2D coordinate traces that are translated by
their starting world \(x, y\), and their axes depend on the arbitrary initial
\texttt{TangentFrame} basis.

\textbf{Alternatives Considered.}
The obvious alternative is to run edge extraction first and then use the final
message pose everywhere. That would make the message simpler, but it would
collapse two different pose meanings into one field: texture-edge pose for the
learning module and curvature pose for surface-distance correction. The current
save-before-overwrite sequence keeps those contracts separate while preserving
the existing Monty message schema.

\subsection{Saving Curvature Pose Before Edge Pose}

\textbf{What it does.}
The save-before-overwrite step preserves the 3D curvature frame produced by
\texttt{ObservationProcessor} before \texttt{\_extract\_2d\_edge} reuses the
same \texttt{pose\_vectors} field for a different purpose. The saved
\texttt{curvature\_pose\_vectors} and \texttt{true\_surface\_normal} are the
geometry inputs for tangent-frame transport and arc-length correction; the
possibly overwritten message pose is the semantic edge pose sent downstream.

\textbf{Algorithm.}
\begin{enumerate}
  \item \texttt{ObservationProcessor} builds a 3D pose matrix from surface
        geometry:
        \[
          \begin{bmatrix}
            \text{surface normal} \\
            \text{first principal curvature direction} \\
            \text{second principal curvature direction}
          \end{bmatrix}
        \]
  \item \texttt{step} saves a copy of that matrix and separately saves a copy
        of row 0, the true 3D surface normal.
  \item If a usable on-object observation is being processed, the tangent frame
        is initialized or transported using \texttt{true\_surface\_normal}.
  \item If edge extraction accepts a texture edge, \texttt{\_extract\_2d\_edge}
        writes a new 2D-local pose matrix back into
        \texttt{morphological\_features["pose\_vectors"]}:
        \[
          \begin{bmatrix}
            [0, 0, 1] \\
            \text{edge tangent in 2D coordinates} \\
            \text{edge perpendicular in 2D coordinates}
          \end{bmatrix}
        \]
  \item The later 2D position update receives the saved curvature pose, not the
        outgoing edge pose. When arc correction is active, rows 1 and 2 of the
        saved matrix remain the principal curvature directions required by
        Euler's curvature formula.
\end{enumerate}

\textbf{Gotchas.}
\texttt{pose\_vectors} means two incompatible things during one call to
\texttt{step}. Before edge extraction, rows 1 and 2 are principal curvature
directions in 3D world coordinates. After accepted edge extraction, rows 1 and
2 are an edge tangent and perpendicular expressed in the 2D tangent-frame
coordinates, while row 0 is the dummy 2D normal \([0, 0, 1]\). Calling
\texttt{get\_surface\_normal()} or \texttt{get\_curvature\_directions()} after
that overwrite returns the edge-pose interpretation, not the original surface
geometry.

\texttt{pose\_fully\_defined} follows the outgoing pose interpretation, not the
saved curvature interpretation. A high-curvature surface can produce a fully
defined principal-curvature frame in the standard observation processor, but
\texttt{TwoDSensorModule} resets the flag to \texttt{False} and sets it back to
\texttt{True} only for an accepted texture edge.

\textbf{Subtle Details.}
The copies are made before edge extraction and before message noise. This
ordering gives \texttt{\_angle\_to\_pose\_2d} the true 3D surface normal for
projecting the image-space edge direction, then gives the displacement update
the same geometric normal for tangent-plane projection. Re-reading the surface
normal from the message after edge extraction would read the 2D-local normal
row \([0, 0, 1]\), which is a coordinate-system convention rather than the
observed 3D surface normal.

\texttt{.copy()} documents ownership. Edge extraction currently replaces the
entire \texttt{pose\_vectors} array, so a simple local reference would still
point at the old array. The copy also protects the saved curvature frame from
future in-place edits to the same array object, which is the safer contract for
a value that is passed to a later mathematical correction.

\textbf{Limitations.}
The save-before-overwrite pattern only preserves the geometry successfully
computed for the current center point. If the standard processor returns
invalid curvature directions or the message lacks usable curvature magnitudes,
the later displacement update falls back to chord-length \((du, dv)\) rather
than corrected arc length.

There is also an implementation mismatch to track separately from this design:
the standard processor writes \texttt{principal\_curvatures} as a
non-morphological feature, while the current 2D position update looks in the
morphological feature dictionary. In that runtime path, the saved curvature
pose is still correct and necessary, but the arc-correction branch is skipped
unless a caller supplies the curvatures where the update currently looks for
them.

\textbf{Alternatives Considered.}
One alternative is to never overwrite \texttt{pose\_vectors}; the message could
carry separate fields such as \texttt{curvature\_pose\_vectors} and
\texttt{edge\_pose\_vectors}. That schema would make the two meanings explicit,
but it would require downstream LM and CMP changes. The current implementation
keeps the existing message shape and isolates the dual use inside the
\texttt{step} method.

Another alternative is to recompute curvature pose after edge extraction. That
would avoid the saved local variables, but it would repeat an expensive
surface-processing step and risk using a different neighborhood or validity
state from the one that produced the outgoing observation. Saving the original
geometry is cheaper and preserves one coherent snapshot for the whole step.

\subsection{\texttt{\_update\_tangent\_frame}}

\textbf{What it does.}
\texttt{\_update\_tangent\_frame(surface\_normal\_3d)} keeps the sensor's
local 2D coordinate frame attached to the observed surface. The first usable
on-object observation creates the frame; later usable on-object observations
parallel-transport that same frame to the new surface normal.

\textbf{Algorithm.}
\begin{enumerate}
  \item Normalize the saved true 3D surface normal. This makes the wrapper
        tolerant of small magnitude drift in upstream normal estimation.
  \item If \texttt{self.\_tangent\_frame} is \texttt{None}, construct a new
        \texttt{TangentFrame}. Its initial \(u\) and \(v\) axes are arbitrary
        tangent-plane axes derived from the normal.
  \item Otherwise, call \texttt{transport(surface\_normal\_3d)} on the existing
        frame. Transport rotates the current \(u\) axis by the minimum rotation
        that carries the previous normal to the new normal, then rebuilds
        \(v = n \times u\).
\end{enumerate}

\textbf{Gotchas.}
The method is called only when the observed state is usable and on object.
Invalid observations and off-object observations do not initialize the frame
and do not advance it. A long off-object interval therefore leaves the last
on-object tangent frame in place until the next usable surface contact.

The initial frame orientation is not canonical. A surface normal defines a
tangent plane, but it does not define the \(u\) and \(v\) axes inside that
plane. \texttt{TangentFrame} chooses those axes from an arbitrary reference
axis, so the first on-object observation fixes the episode's local 2D axes.
Two episodes that start from different surface normals get different initial
2D coordinate frames even on the same object.

\textbf{Subtle Details.}
The same \texttt{TangentFrame} object is transported rather than recreated.
This preserves the accumulated orientation of the local 2D chart. Recreating a
new frame at each step would choose a fresh arbitrary tangent basis from the
new normal, causing the meaning of \((du, dv)\) to rotate or jump between
successive observations. The unit test that checks transport-not-recreation
asserts that the frame object after the second step is the same object created
on the first step.

Transport depends on the saved \texttt{true\_surface\_normal}, not the
outgoing edge pose. After edge extraction, the message pose normal is the
2D-local row \([0, 0, 1]\). Transporting against that row would align the frame
to a message convention instead of the actual 3D surface normal.

The re-orthonormalization happens inside \texttt{TangentFrame.transport}, not
inside this wrapper. After rotation, the transported \(u\) vector is projected
back into the tangent plane and normalized, then \(v\) is recomputed as
\(n \times u\). This keeps repeated transports from accumulating floating-point
drift over long trajectories.

\textbf{Limitations.}
The frame encodes a local unrolling path, not an object-intrinsic coordinate
system. Its orientation depends on the first surface normal and on the path of
subsequent transported normals. Starting the same object from a different
surface point changes the initial tangent basis and therefore rotates the
resulting 2D trace.

The wrapper normalizes the supplied normal and has no local fallback for a
near-zero vector. If upstream surface-normal estimation produced a near-zero
normal while still marking the observation usable, \texttt{normalize} would
raise a \texttt{ValueError}. The intended guard is the
\texttt{ObservationProcessor} validity path, which sets \texttt{use\_state}
false when surface geometry is not valid.

\textbf{Alternatives Considered.}
One alternative is to define \(u\) and \(v\) directly from world axes at every
step. That would make each frame deterministic from the current normal alone,
but it would add arbitrary twist whenever the normal crosses the reference-axis
singularity or moves around curved geometry. Parallel transport instead
preserves the previous in-plane orientation and introduces only the rotation
required by the changing surface normal.

Another alternative is to express displacement in a fixed world frame and skip
tangent-frame transport. That works only on surfaces whose tangent plane is
approximately fixed. On a curved surface, the fixed world frame stops matching
the local tangent plane, so accumulated \((x, y)\) displacement no longer
represents surface travel in the unrolled 2D chart.

\subsection{\texttt{\_update\_2d\_position\_and\_displacement}}

\textbf{What it does.}
\texttt{\_update\_2d\_position\_and\_displacement} rewrites the outgoing
message location and displacement from 3D sensor coordinates into the
accumulated 2D surface chart. It uses the transported tangent frame to express
the current 3D step as \((du, dv)\), then stores the result in a 3D-shaped
message with a dummy zero \(z\) coordinate.

\textbf{Algorithm.}
\begin{enumerate}
  \item If the observation is off object, set displacement to \([0, 0, 0]\) and
        return without changing the saved previous 3D or 2D locations.
  \item Copy \texttt{observed\_state.location} into
        \texttt{current\_3d\_location}. This preserves the real 3D position
        before the method overwrites the outgoing message location with its 2D
        representation.
  \item If there is no previous 3D location, seed
        \texttt{\_previous\_3d\_location} from the current 3D point and seed
        \texttt{\_previous\_2d\_location} from the current world \(x, y\). Emit
        location \([x, y, 0]\) and return.
  \item Compute the 3D displacement from the previous on-object 3D point to the
        current 3D point, then project that displacement onto the tangent plane
        of the saved true surface normal.
  \item If the projected tangent displacement has norm below
        \texttt{DEFAULT\_TOLERANCE}, update the previous 3D location, emit zero
        displacement, keep the previous 2D location unchanged, and return.
  \item Express the tangent displacement in the current transported frame:
        \[
          du = d_{\mathrm{tan}} \cdot u,
          \qquad
          dv = d_{\mathrm{tan}} \cdot v
        \]
        where \(u\) and \(v\) are \texttt{basis\_u} and \texttt{basis\_v}.
  \item If curvature magnitudes and saved curvature pose vectors are available,
        pass \((du, dv)\) through \texttt{arc\_length\_corrected\_displacement}
        so chord-length components become local surface arc lengths.
  \item Add the final \((du, dv)\) to \texttt{\_previous\_2d\_location}, save
        the current 3D point as the new previous 3D location, set displacement
        to \([du, dv, 0]\), and set outgoing location to
        \([x_{2d}, y_{2d}, 0]\).
\end{enumerate}

\textbf{Gotchas.}
The first on-object observation initializes location state but does not emit a
displacement field. Off-object observations explicitly emit zero displacement,
and later on-object movement emits \([du, dv, 0]\), but the first contact is a
seed rather than a movement measurement. Any downstream code that assumes every
message has a displacement field must handle the first on-object message
separately.

Off-object observations do not reset \texttt{\_previous\_3d\_location} or
\texttt{\_previous\_2d\_location}. The next on-object displacement is measured
from the last on-object 3D point, not from the off-object sample. This preserves
the last known surface coordinate through brief off-object observations, but a
large return jump is accumulated as one surface displacement.

The method does not check whether the message should be used as a percept. In
\texttt{step}, it runs after message noise and after motor-only handling can
disable percept use. A motor-only message can therefore update the private 2D
trajectory even though the resulting message is not meant to be used by an LM.

\textbf{Subtle Details.}
The copy of \texttt{current\_3d\_location} is load-bearing. By the end of the
method, \texttt{observed\_state.location} no longer contains the real 3D sensor
location; it contains the accumulated 2D location embedded as \([x, y, 0]\).
Without the saved copy, later updates to \texttt{\_previous\_3d\_location} would
accidentally store the rewritten 2D coordinate instead of the observed 3D point.

The near-zero tangent branch updates the previous 3D location but leaves the
previous 2D location unchanged. This is the right behavior for movement along
the surface normal or numerical jitter: the sensor has a new 3D reference point
for the next step, but it has not moved across the unrolled surface chart.

Projection happens before expressing the step in the tangent-frame basis. This
removes displacement along the surface normal, so \((du, dv)\) measures motion
within the tangent plane instead of raw Euclidean motion in world coordinates.
The current \texttt{TangentFrame} basis is then used only as coordinates for
that already-tangent vector.

\textbf{Limitations.}
The first 2D location is seeded from world \(x, y\), not from a canonical
object-intrinsic origin. The accumulated coordinates therefore carry the
translation and orientation of the first contact convention. They are useful as
a continuous local chart within an episode, but they are not automatically
aligned across episodes that start elsewhere on the object.

The outgoing 2D state is encoded as a 3-vector for Monty message compatibility.
The third coordinate in both location and displacement is fixed at zero and
does not represent depth, height, curvature, or any other geometric quantity.

The arc-correction branch currently depends on curvature magnitudes being
present in the morphological feature dictionary. The standard observation
processor writes that value as a non-morphological feature, so the default path
uses chord-length \((du, dv)\) unless a caller supplies curvature magnitudes
where this method currently looks for them.

The method is private and relies on \texttt{step} to update the tangent frame
before any nonzero on-object displacement is processed. A direct call with a
previous 3D location but no \texttt{\_tangent\_frame} would fail when accessing
\texttt{basis\_u} and \texttt{basis\_v}.

\textbf{Alternatives Considered.}
One alternative is to reset the previous locations whenever the sensor goes
off object. That would avoid accumulating a large jump when contact resumes,
but it would also fragment a trajectory whenever the detector briefly loses
surface contact. The current behavior treats off-object messages as zero-motion
gaps and preserves the last known surface coordinate.

Another alternative is to emit raw world \(x, y\) on every step. That is simpler
and matches flat surfaces aligned with the world \(xy\)-plane, but it fails on
curved surfaces because the visible local surface moves through changing
tangent planes. Accumulating tangent-frame displacements preserves a continuous
unrolled chart instead.

Emitting a true 2-vector would make the 2D convention explicit, but it would
break the existing Monty message contract that locations and displacements are
3-vectors. The dummy \(z=0\) coordinate keeps the message shape compatible while
making the 2D reduction local to this sensor module.

\subsection{Location and Displacement Conventions}

\textbf{What it does.}
This convention layer keeps \texttt{TwoDSensorModule} compatible with Monty's
3D message schema while using the first two coordinates as an accumulated 2D
surface chart. The outgoing message still contains 3-vector locations and
3-vector displacements, but the third coordinate is a dummy 2D channel fixed at
zero.

\textbf{Algorithm.}
\begin{enumerate}
  \item Receive the real 3D sensor location from \texttt{ObservationProcessor}.
        This is the geometric location used internally to compute movement.
  \item On the first on-object contact, initialize the private 2D state from
        the real world \(x, y\) coordinates and emit location \([x, y, 0]\).
  \item On later on-object contacts, compute an incremental tangent-frame
        displacement \((du, dv)\), add it to the private accumulated 2D
        location, and emit location \([x_{2d}, y_{2d}, 0]\).
  \item Emit displacement as \([du, dv, 0]\) for nonzero tangent movement, and
        as \([0, 0, 0]\) for off-object observations or near-zero tangent
        movement. The first on-object contact seeds state and does not emit a
        displacement field.
\end{enumerate}

\textbf{Gotchas.}
The \(z\) coordinate in the outgoing message is not a height coordinate. It is
always zero after the 2D position rewrite. Code that compares
\texttt{TwoDSensorModule} locations against 3D sensor-module locations must not
interpret matching shape as matching semantics.

The first two coordinates change meaning after the first on-object contact.
The first emitted location uses the world \(x, y\) of the contact point. Later
locations are accumulated tangent-frame displacements added to that seed. On a
flat world-\(xy\)-aligned surface those values match raw world \(x, y\); on a
curved surface or a differently oriented visible plane they are local chart
coordinates, not raw world coordinates.

The displacement field is incremental while the location field is accumulated.
\([du, dv, 0]\) describes the current step in the transported tangent frame;
\([x_{2d}, y_{2d}, 0]\) describes the accumulated position in the episode's 2D
chart. Treating displacement as an absolute 2D location would double-count
movement or collapse the trajectory to per-step offsets.

\textbf{Subtle Details.}
The use of world \(x, y\) as the first seed is a compatibility convention, not a
claim that the object has a world-\(xy\) intrinsic 2D coordinate system. It gives
the first message a concrete 3-vector location without introducing a new origin
field. After that, the transported tangent frame, not the world axes, defines
the incremental coordinate directions.

The dummy \(z=0\) coordinate keeps the message shape compatible with CMP and
with learning-module code that expects 3-vectors. This avoids a schema split
between 2D and 3D sensor modules, but it pushes the burden of interpretation
onto the sensor-module contract: consumers must know that this sender's third
coordinate carries no geometric information.

\textbf{Limitations.}
The convention does not make 2D traces automatically comparable across
episodes. Different first contact points translate the chart, and different
initial tangent-frame bases rotate it. A downstream learning module must either
handle those differences or the system must provide an external canonical
alignment.

The convention is explicitly aligned with views whose relevant projection is
world \(xy\). The class docstring calls out the failure mode: for a camera
looking along the world \(x\)-axis, the visible plane is closer to \(yz\), but
the initial emitted 2D location still uses world \(x, y\). In that view, the
seed coordinate does not match the visible image plane.

The first on-object message can contain a rewritten 2D location without a
displacement field. This is consistent with the state-machine semantics: no
previous on-object point exists yet, so there is no measured step. Consumers
that require displacement on every used state need an explicit first-contact
fallback.

\textbf{Alternatives Considered.}
One alternative is to emit a true 2-vector for 2D locations and displacements.
That would make the coordinate dimensionality explicit, but it would require
separate message handling in CMP and downstream learning modules. The current
3-vector encoding preserves the existing schema.

Another alternative is to define the first 2D location as \([0, 0, 0]\) and
store all positions relative to first contact. That would remove the inherited
world-\(xy\) translation, but it would also change the apparent location scale
seen by existing consumers and would require a separate way to recover the
contact point if needed for logging or alignment.

A third alternative is to seed from the camera image plane rather than world
\(x, y\). That would better match views that are not world-\(xy\)-aligned, but
it would require a camera-frame convention for every sensor orientation. The
current implementation keeps the seed simple and documents that non-\(xy\)
views need a different projection convention.
