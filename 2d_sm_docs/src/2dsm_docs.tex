\section{Introduction}

This document is a reference manual to \href{https://github.com/thousandbrainsproject/tbp.monty}{\texttt{TwoDSensorModule}} as implemented in \texttt{tbp.monty} version \texttt{0.33.0}. The document will cover results and explanation of how and why certain algorithms are implemented, and also point out limitations and areas for improvement. The manual will be detailed enough for someone who is interested in improving any part of the TwoDSensorModule to have a good understanding on why certain things were chosen and get a guide for where to go.

The implementation of TwoDSensorModule was roughly divided into two phases:

\begin{enumerate}
  \item Detecting dominant edge in a patch
  \item Implementing 2D Movement
\end{enumerate}

\subsection{\texttt{EdgeDetector}}

\textbf{The Problem.}
This feature was initially posed as an edge detection problem, but the
actual problem is more specific. The 2D sensor does not only need to know
whether an edge exists at a single center pixel. It needs to know whether
there is a dominant edge in the observed $64 \times 64$ patch and, if so,
what orientation that edge has. This is different from other local feature
extractors that read the feature value at the patch center. Texture edges
can pass near the center, occupy only part of the patch, or appear together
with other weaker edges. The detector therefore needs a notion of dominant
orientation that is global enough to be stable but still biased toward the
center of the patch.

The same image at different zoom levels can produce different dominant edge
orientations. A line that fills most of the patch at one scale can become a
small off-center detail at another scale. For this reason the patch size,
radial weighting, and detection thresholds are part of the algorithm rather
than incidental implementation details.

\textbf{The Solution.}
The main algorithm that performs dominant edge detection, orientation
estimation, edge strength computation, and coherence computation is
implemented by the \texttt{\_\_call\_\_} method of \texttt{EdgeDetector}.
The class replaces the
earlier standalone \texttt{compute\_edge\_features} function while
preserving the same conceptual algorithm. The callable class structure lets
\texttt{TwoDSensorModule} hold a configured detector instance and establishes
the pattern for future feature detectors.

Given a \texttt{SensorObservation}, the detector first extracts
\texttt{observation["rgba"][:, :, :3]} and interprets those channels as RGB.
This is upheld by the current \texttt{SensorObservation} path, where the
color patch is RGBA with red, green, and blue in that order. A caller that
constructs observations from images loaded with OpenCV must be careful:
\texttt{cv2.imread} returns BGR, so such images need to be converted to RGB
before being placed in the \texttt{rgba} field. Otherwise
\texttt{cv2.COLOR\_RGB2GRAY} uses the wrong luminance weights, which can
shift the gradients and the resulting edge orientation.

The detector then converts the RGB patch to grayscale and computes Sobel
gradients:
\[
  I_x = \texttt{Sobel}(I, 1, 0), \quad
  I_y = \texttt{Sobel}(I, 0, 1)
\]
From these gradients it builds a per-pixel structure tensor:
\[
  J =
  \begin{bmatrix}
    I_x^2 & I_x I_y \\
    I_x I_y & I_y^2
  \end{bmatrix}
\]
Each tensor component is Gaussian-smoothed before aggregation. This order is
intentional: smoothing $I_x^2$, $I_y^2$, and $I_x I_y$ estimates the local
second-moment structure, whereas smoothing $I_x$ and $I_y$ first and then
squaring would suppress opposing gradients before they contribute to the
orientation estimate.

The per-pixel tensors are then reduced to one representative tensor for the
patch using a center-biased weight map:
\[
  w(r, c) =
    \exp\left(-\frac{d(r, c)^2}{2\sigma_r^2}\right)
    \left(I_x(r, c)^2 + I_y(r, c)^2\right)
\]
with weights outside \texttt{radius} set to zero. The radial term makes
central gradients count more than peripheral gradients, while the gradient
magnitude term makes flat pixels contribute zero. This is what lets the
detector estimate a dominant patch-level edge without becoming a pure
whole-image average.

The aggregated tensor has two eigenvalues, $\lambda_{\min}$ and
$\lambda_{\max}$. Edge strength is defined as $\sqrt{\lambda_{\max}}$.
Coherence is defined as:
\[
  \frac{\lambda_{\max} - \lambda_{\min}}
       {\lambda_{\max} + \lambda_{\min}}
\]
with a zero fallback when the eigenvalue difference is below tolerance.
Coherence measures how strongly the patch evidence prefers one orientation:
it is high for a clean single edge and low for isotropic texture, corners, or
multiple competing edge directions. The final boolean
\texttt{has\_edge} is true only when edge strength exceeds
\texttt{strength\_threshold} and coherence exceeds
\texttt{coherence\_threshold}.

\textbf{Center Bias and \texttt{max\_center\_offset}.}
Radial weighting and \texttt{max\_center\_offset} solve different problems.
Radial weighting is continuous and always participates in the orientation
estimate: it downweights gradients far from the center but still allows a
strong off-center edge to influence the aggregate. By contrast,
\texttt{max\_center\_offset} is an optional hard rejection rule. Once an
orientation has been estimated, the detector projects the weighted gradient
evidence onto the detected edge normal and computes how far the weighted edge
centerline is from the patch center. If that distance is larger than
\texttt{max\_center\_offset}, the detector returns no edge.

The default value is \texttt{None}, so this hard center check is disabled.
The option is mainly useful for reducing extra edge clutter during
visualization. It does not replace radial weighting, because it operates
after the dominant orientation has already been estimated.

\textbf{Geometric Edge Check.}
\texttt{EdgeDetector} also checks whether the detected RGB edge corresponds
to a depth discontinuity. It computes Sobel gradients on the depth patch,
takes the depth gradient at the center pixel, and projects that gradient onto
the direction perpendicular to the RGB edge. If this perpendicular depth
gradient exceeds \texttt{depth\_edge\_threshold}, the edge is marked as a
geometric edge.

This matters because \texttt{TwoDSensorModule} is interested in texture
edges on a 2D surface, such as the edge of a logo on a mug, not object
boundaries or surface creases. \texttt{EdgeDetector} only reports
\texttt{is\_geometric\_edge}; the filtering decision happens in
\texttt{TwoDSensorModule.\_extract\_2d\_edge}. The default
\texttt{depth\_edge\_threshold} is \texttt{0.01}, which corresponds to about
one centimeter when depth is measured in meters.

\textbf{Parameter Choices and Limitations.}
Several defaults are pragmatic rather than analytically derived.
\texttt{kernel\_size=7} is a remnant from an earlier version that focused on
edges in a small center region. \texttt{radius=14.0} was chosen as a
reasonable center neighborhood for a $64 \times 64$ patch.
\texttt{sigma\_r=7.0} controls the radial Gaussian falloff, but its exact
value has not been justified independently. \texttt{coherence\_threshold=0.5}
is a middle-of-range requirement on a score bounded between 0 and 1.
\texttt{strength\_threshold=0.1} is intentionally low so weak but coherent
texture edges are still detected.

The detector returns one dominant orientation. It cannot represent two edges,
a corner, a junction, or repeated strokes in the same patch except by reducing
coherence or producing a compromise orientation. The geometric edge check is
also center-pixel based: it computes the full depth gradient image but samples
only the center depth gradient for classification. A noisy center depth value
can therefore mark a texture edge as geometric, or miss a depth discontinuity
that is nearby but not centered.

\textbf{Alternatives.}
We explored well-known edge detection methods such as Canny edge detection,
but Canny returns an edge-pixel mask rather than a compact dominant
orientation, strength, and coherence for a patch. A single-pixel Sobel angle
at the patch center would be closer to the old center-feature interpretation,
but it is brittle when the edge is slightly off center or noisy at the exact
center. A Gabor filter bank could test for edges at several orientations, but
it requires choosing a discrete orientation grid and running multiple
convolutions. The structure tensor gives a continuous orientation estimate in
one pass while still allowing center bias through the weight map.

\subsection{\texttt{TangentFrame}}

\textbf{The Problem.}
As the 2D sensor moves across a curved 3D surface, we need to express
sensor displacement in a consistent 2D coordinate frame. On a flat
surface a fixed $(u, v)$ pair suffices, but on a curved surface the
tangent plane rotates with the curvature. Naively accumulating
displacement vectors in a fixed world frame causes the tracked position
to drift off the surface.

\textbf{The Solution.}
\texttt{TangentFrame} maintains a right-handed orthonormal basis
$(u, v, n)$, where $n$ is the current surface normal, $u$ is the
horizontal tangent direction, and $v$ is the vertical tangent direction.
As the sensor moves to a new surface point, the method
\texttt{transport(new\_normal)} updates the basis via
\emph{parallel transport}---the unique minimum-rotation update that
keeps $u$ and $v$ in the new tangent plane without introducing
extraneous twist. This is the discrete analogue of parallel-transporting
a vector along a geodesic on a Riemannian manifold
(\texttt{https://en.wikipedia.org/wiki/Parallel\_transport}).

\textbf{Initialization.}
Given an initial surface normal $n$, the constructor builds $u$ and $v$
as follows. It picks an arbitrary reference axis $a = [0, 1, 0]$,
falling back to $a = [0, 0, 1]$ if $n$ is nearly parallel to $a$
($|\cos\theta| > 1 - \epsilon$). Then:
\begin{align*}
  u &= \mathrm{normalize}(a \times n) \\
  v &= \mathrm{normalize}(n \times u)
\end{align*}
The cross products ensure $u$ lies in the tangent plane and $(u, v, n)$
forms a right-handed frame.

\begin{figure}[h]
  \centering
  \includegraphics[width=0.8\textwidth]{../imgs/tangent_frame_init.png}
  \caption{Initialization of the orthonormal tangent frame $(u, v, n)$ from a surface normal $n$.}
\end{figure}

\textbf{Parallel Transport.}
When \texttt{transport(new\_normal)} is called with a new surface normal
$n'$, the update proceeds in three steps:
\begin{enumerate}
  \item Compute the rotation $R$ that maps $n \to n'$ via the
    axis-angle representation:
    \[
      \text{axis} = \mathrm{normalize}(n \times n'), \quad
      \theta = \arccos(\mathrm{clip}(n \cdot n', -1, 1))
    \]
  \item Apply $R$ to $u$: this keeps $u$ as close as possible to its
    previous direction while moving it into the new tangent plane.
  \item Re-orthonormalize to suppress floating-point drift accumulated
    over many steps:
    \[
      u \leftarrow \mathrm{normalize}(u - (u \cdot n') \, n'),
      \quad v \leftarrow n' \times u
    \]
\end{enumerate}
Step 3 is necessary because repeated small rotations accumulate
numerical error; projecting $u$ back onto the tangent plane and
recomputing $v$ from scratch keeps the frame exactly orthonormal.

  \centering
  \includegraphics[width=0.6\textwidth]{../imgs/tangent_frame_transport.png}
  \caption{Parallel transport of the tangent frame from normal $n$ to a new normal $n'$.}
\end{figure}

\subsection{\texttt{arc\_from\_projection} and Arc-Length Correction}

\textbf{The Problem.}
When the sensor moves along a curved surface, the displacement we observe is a
chord in the tangent plane, not the true distance traveled along the curve.
On a convex surface the sensor must travel further than the straight-line
projection suggests; without correction, accumulated 2D positions are
systematically compressed relative to the actual surface path.

\textbf{The Solution.}
At each surface point we fit an \emph{osculating circle}: the unique circle
that is tangent to the surface and has the same normal curvature $k$ in the
direction of movement. The osculating circle is the best local circular
approximation to the curve, in the sense that it agrees with the curve up to
second order. The approximation holds well when curvature is approximately
constant over the displacement, but becomes inaccurate for surfaces with
rapidly varying curvature (e.g., a sharp ridge crossed in a single large step).

Under this assumption the relationship between tangent-plane chord $p$ and
arc length $s$ is:
\[
  p = \frac{\sin(k \cdot s)}{k}
  \quad\Longrightarrow\quad
  s = \frac{\arcsin(k \cdot p)}{k}
\]
This is implemented in \texttt{arc\_from\_projection(tangent\_projection, curvature)}.
Two guard conditions keep the formula numerically safe:
\begin{itemize}
  \item $|k \cdot p| < 0.001$: the surface is nearly flat over the step, so
        $\arcsin(k p) \approx k p$ and no correction is applied.
  \item $|k \cdot p| \geq 1.0$: the chord exceeds the radius of curvature,
        meaning the sensor has moved past the most extreme visible point under
        the constant-curvature assumption. The correction is skipped and a
        warning is logged; the proper remedy is a policy that takes smaller 3D
        steps.
\end{itemize}
The formula is sign-preserving (\texttt{np.copysign}) and works for both
convex ($k > 0$) and concave ($k < 0$) surfaces because the arc-to-chord
geometry on a circle is the same regardless of the sign of curvature.

\textbf{Helper: \texttt{directional\_curvature}.}
Before correcting displacement we need the normal curvature $k$ in the
direction of movement. Given principal curvatures $k_1, k_2$ and their
directions $\hat{d}_1, \hat{d}_2$, Euler's curvature formula gives:
\[
  k(\theta) = k_1 \cos^2\theta + k_2 \sin^2\theta
\]
where $\theta$ is the angle between the movement direction and $\hat{d}_1$.
\texttt{directional\_curvature} validates that $\hat{d}_1$ and $\hat{d}_2$
are orthonormal and that the movement direction lies in their span before
applying this formula.

\textbf{Helper: \texttt{arc\_length\_corrected\_displacement}.}
This function ties the two helpers together. Given tangent-frame displacements
$(du, dv)$ along basis vectors $(u, v)$, it:
\begin{enumerate}
  \item Calls \texttt{directional\_curvature} once for $u$ and once for $v$
        to obtain $k_u$ and $k_v$ from the observed principal curvatures and
        their pose vectors.
  \item Passes each chord-displacement through \texttt{arc\_from\_projection}
        to obtain arc-length-corrected displacements $(\hat{u}, \hat{v})$.
\end{enumerate}
The result is a pair of corrected 2D displacements that accurately reflect the
distance the sensor traveled along the surface in each tangent direction.
